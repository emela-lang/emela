# 字句解析の補足

仕様（草案 2026-10-07）に書かれていない判断を残す．

- （補）空白はスペースとタブ．`\r\n` は `\n` と同じく1つの NEWLINE にする．単独の `\r` は認識できない文字として扱う
- （補）コメントは `\r` の手前で終わる（`\r\n` の `\r` をコメントに含めない）
- （補）小文字名は 17.2 の EBNF どおり大文字を含んでもよい（`userId` を通す）．snake_case かどうかは lint に任せる
- （補）型名は EBNF どおり大文字が続いてもよい（`HTTPServer` は型名）
- （補）どのクラスにも合わない名前（`Http_client` など）は，単語まるごとを ERROR_TOKEN 1つにして診断を1件出す
- （補）名前に使える文字は ASCII だけ．`é` などは認識できない文字になる
- （補）数値の直後に英字が続くもの（`1e9` `1.0e` `3px`）は，かたまりを ERROR_TOKEN 1つにして診断を出す．EBNF にない小数点なしの指数もここに入る
- （補）`1..2` は INT DOT2 INT，`1.x` は INT DOT LOWER_NAME（小数点の後ろに数字がなければ浮動小数点にしない）
- （補）文字列は改行をまたげない．改行に着いたら「閉じていない」の診断を出し，改行はコードとして読む
- （補）文字列は STRING_QUOTE / STRING_TEXT / INTERP_START / INTERP_END に分け，パーサが組み立てる．エスケープは STRING_TEXT の中に含めたまま，不正なものは `\` と次の1文字の範囲に診断を出す
- （補）補間の中は普通のコードなので，コメントや改行を含みうる
- （補）継続判定は改行の次の「意味のあるトークン」を見る．間の空白，コメントだけの行，空行は飛ばす（`a⏎# c⏎|> f` の改行は2つとも継続）
- （補）補間 `#{ }` の中の改行は `(` の中と同じく継続にする
- （補）2.5 の穴3つは，どれも継続にする．`}⏎else`，行頭の `->`，行頭の `|` はどれも文を始めることがないので，継続にしても曖昧さは生まれない．`} else {` などへの揃えは fmt が行う

- （補）16進と2進の接頭辞の誤り（`0XFF` `0o17` `0x`），16進と2進の小数（`0x1.5`）は，かたまりを ERROR_TOKEN 1つにして E0104 を出す
- （補）`\u{...}` の形の崩れ（`{` や `}` がない，桁数が1〜6でない）も，サロゲートや 10FFFF 超えと同じ E0108 にする．範囲は `\` から読めたところまで
- （補）複数行の文字列は，開く `"""` と閉じる `"""` を TRIPLE_QUOTE にする．閉じる側は行頭の空白を含み，その空白が各行から取り除くインデントになる．本文は STRING_TEXT で，改行を含む．開く `"""` の直後の改行は最初の STRING_TEXT に，閉じる行の直前の改行は最後の STRING_TEXT に入るので，値を作る側（lowering）がこの2つとインデントを取り除く
- （補）複数行の文字列の形の誤り（開く `"""` の後ろが改行でない，閉じる `"""` が行に1つでない，閉じる行より浅い行）はまとめて E0109 にする．字句の帯（E0101〜E0109）に空きがないため．浅さはバイトの前方一致で見るので，閉じる行と違う空白（タブと空白の混在）も誤りになる．閉じる `"""` が行に1つでないときはインデントの検査をしない
- （補）複数行の文字列の中の行末の `\` は E0106 を出し，本文を読み続ける
- （補）`""""` は `"""` と `"` に切る（最長一致）

# パーサの補足

- （補）効果の集合 `use { ... }` の波括弧の中の改行は読み飛ばす．17.1 で取り除かれるのは `(` `[` の中の改行だけなので，波括弧の中の改行は字句では区切りとして残る．複数行に分けて書けるようにパーサで読み飛ばす
- （補）パターンの負の数（6.5，17.6）は，`-` と数値を1つの LITERAL_PAT に入れる．`-` と数の間の空白は許し（`- 1`），fmt が `-1` に詰める．`-` の後ろが数のリテラルでなければ（`-x`），今までどおり E0113 にする．暫定の E0116 は外したので，コードは欠番になる
- （補）束縛の左辺の `-1`（`(-1, x) = p`）は，式としては単項マイナスの PREFIX_EXPR なので，木ができた後の検査（`validation.rs`）で，`-` の後ろが数のリテラルだけのときにパターンとして通す．17.6 の pattern は束縛の左辺にも使われるため．`--1` や `-x` は E0125
- （補）パターンの文字列リテラルに補間があれば E0117 を出し，補間の中身は ERROR に包む．補間は定数でないので照合に使えない
- （補）要素が1つのタプル `(Int,)` `(a)` `(a,)` は E0112 を出し，タプルとして読む．型の `(Int)` は括弧の型（PAREN_TYPE）で，診断を出さない（5.5，17.4 の改訂）
- （補）式の `(a)` は括弧の式，`(a,)` は E0112 を出してタプルにする．パターンの `(a)` はタプルの誤りとして扱う
- （補）`use X` の直後に `.` か `(` が来たら E0121 を出す（17.5 の「`(use X).op(...)` と括弧で囲む」を診断にした）
- （補）閉じていない `(` の中では改行が継続になり NEWLINE が来ないので，パーサは「直前に改行があるか」をトークンごとに持ち，行頭を文の区切りとして扱う．行頭の宣言キーワード（`fn(` を除く）はエラー回復の同期点にする
- （補）`derive` は次の行に書ける（10.5 の例 `type User(...)⏎  derive Eq`）．文法どおりだと行頭の `derive` の前の改行は区切りになるので，パーサが改行を先読みして吸収する．継続の判定（2.5）と同じく，間のコメントだけの行と空行は飛ばす
- （補）宣言と `derive` の間のドキュメントコメント `##` は DERIVE_CLAUSE の中に入れる．`derive` は宣言ではないので，型や enum のドキュメント（`doc_comments`）には含めない．型の説明は宣言の前に書く
- （補）ドキュメントコメント `##` は直後の宣言，バリアント，フィールド，effect の操作，handler の項目のノードの中に入れる．`##` の後ろの改行は区切りとして字句に残るので，パーサは区切りの改行を読むときにコメントの位置から宣言を開く
- （補）宣言の本体（effect，handler，trait，impl）の中では，行頭の `fn` と `suspend` をエラー回復の同期点にしない．本体の項目がそれで始まるため
- （補）trait の本体の `derive` で始まる項目（導出規則，18.1 #3 で構文が未確定）は E0129 を出し，対応の取れた `}` まで ERROR に包む
- （補）`@external` が要る宣言（本体のない fn，トップレベルの suspend fn，フィールドのない type）の検査は，トップレベルの宣言だけに掛ける．trait の fn は本体を省ける
- （補）エフェクトの操作の `use` 節（E0137，8.1）はパーサでは読み，validation で節の範囲に出す．impl の fn の E0136 と同じ形．読んでおくので，後ろの `{` や改行で構文エラーを重ねない
- （補）効果の集合の要素は，エフェクト（type_ref）と集合の型引数（大文字名）を順を問わず混ぜて読む（`use { Quiet, R }`，17.4）．どちらの種類かは名前解決と型推論で決める
- （補）名前付き型の型引数（TYPE_ARG_LIST の要素）には集合も書ける（9.2 の `Handler[NotFound | Timeout, { Db, Log }]`）．17.4 の `type` の並びを `type_arg = type | effect_set の波括弧の形 | error_item "|" error_item { "|" error_item }` に広げた．`{` で始まれば EFFECT_SET（`{}` を含む），名前（`A`，`Mod.A`）の直後が `|` なら ERROR_SET，それ以外は型として読む．要素1つの `NotFound` は今までどおり PATH_TYPE．どの型引数が集合を受けるかはパーサでは見ず，型推論が確かめる（E0323，E0324）．型引数の外（引数の型の最上位など）には集合を書けない
- （補）引数の並びの `..` は，部分更新の `..式` も束縛の左辺の式のない `..` も SPREAD_ARG にする（リストの REST_EXPR とは分ける）．`..` の後ろの引数は E0114．呼び出し先が構成子かどうかはパーサでは見ず，関数の呼び出しに書いたときの誤りは名前解決か型検査で出す．束縛の左辺に `..式` を書けば E0125
- （補）本体のない fn とトップレベルの suspend fn は，`@external` に加えて `@intrinsic`（同梱の core のソースの組み込み関数）でも許す．`@intrinsic` を同梱のソースの外で使ったか，本体のない fn 以外に付けたかは名前解決が見る（E0224，E0225）
- （補）`@external` の引数の形（12.1，12.3）は validation で見る．fn の注釈は `(ターゲット, "a")` か `(ターゲット, "a", "b")` だけ．引数のない `@external` と `@external()` も，ターゲットの名前がないので E0138．最初の引数が名前でない，ターゲットの後ろに文字列でない引数（数，名前，`k: "v"`）がある，文字列が1つか2つでない，も E0138．最初の引数が名前でなければ，その注釈の残りは見ない
- （補）`@external` の文字列に補間（`"#{x}"`）を書けば E0138．複数行の文字列は文字列として通す
- （補）`@external` のターゲットとして知っている名前は `js` と `wasm` だけ．ほかの名前は E0140．仕様はターゲットの一覧を書いていないので，出力の段（16章）が増えたらここに足す
- （補）1つの fn の同じターゲットの `@external` は，2つ目以降のターゲットの名前に E0139．知らないターゲットは E0140 だけを出し，重複は数えない
- （補）`@external type` の注釈に引数の並びがあれば，空の `()` でも E0141（12.3）．同じ type に引数のない `@external` が2つあっても診断しない
- （補）引数の読めなかった注釈（中に ERROR があるもの）は，構文の診断が出ているので `@external` の形を見ない
- （補）エフェクトの型引数（8.1）．`effect State[S]` の型引数は type や enum と同じ TYPE_PARAM_LIST．`handler H: State[Int]` と `use State[Int]` の型引数は，PATH の後ろの兄弟の TYPE_ARG_LIST にする（HANDLER_EFFECT と USE_EXPR の PATH の親は今までどおり）．効果の集合の要素の `State[Int]`（`use { State[Int], Log }`）は，PATH と TYPE_ARG_LIST を PATH_TYPE で包む．集合の中では要素ごとに型引数を対応させるため．型引数を書かなければ今までどおり PATH だけ
- （補）17.4 の `effect_item = type_ref | upper_name` を `type_ref [ "[" type { "," type } "]" ] | upper_name` に広げた（指示書の `use { State[Int], Log }`）．17.3 の handler_decl と 17.5 の `use` は仕様の文法どおり．並びの中身は名前付き型の型引数と同じ type_arg で読み，集合を書いたら型推論が E0324 にする．空の `[]` も読む（fn の型引数の `[]` と同じ）
- （補）エフェクトの操作の型引数（17.3 の op_sig の `[ type_params ]`）は，fn の宣言と同じ TYPE_PARAM_LIST として名前の直後に読む．組み込みのエフェクトだけに許すことは型検査が見る（E0426）
- （補）`await` を将来のための予約語（3.3）から外した．11.5 の `Fiber.await` と 11.7 の `Deferred.await` が関数名に使うため（進行役と合意．仕様の 3.3 の更新は進行役が持つ）
- （補）2.5 の規則4（シグネチャの中の `fails` と `use` で始まる行は続き）は字句の継続の判定（`lexer/continuation.rs`）で行う．`fn` の直後が小文字の名前なら（fn の宣言と effect の操作．`fn(` のラムダと関数型は除く）シグネチャを開き，その括弧の深さで `{` が来るか，続かない改行が来たら閉じる．本体のない宣言（effect の操作，`@external` の fn）は改行で閉じるので，次の宣言の行頭の `fails`／`use` は続きにならない．`fails` は文脈依存の語で小文字の名前として字句になるので，ソースの文字列で見る
- （補）後置の match（6.5）は escape と同じ位置（17.5 の expr の末尾の繰り返し）で読み，MATCH_EXPR の子は「対象の式，`match`，MATCH_ARM_LIST」の順になる．前置と子の並びが入れ替わるだけで，対象は最初の式の子のままなので，名前解決から先は変えていない
- （補）前置の `match x { 腕 }` は，`match` の位置に E0142 を出し，前置の形のまま MATCH_EXPR として読んで先へ進む（腕の検査と型推論を続けるため）．`1 + match x {...}` のように演算子のオペランドの位置でも同じ
- （補）2.5 の規則1の `match` は，`match` の次の意味のあるトークンが `{` のときだけ前の行に続ける．`match` の後ろが `{` でなければ前置の match なので，新しい文として読んで E0142 を出す（続けてしまうと「`{` がない」という分かりにくい誤りになる）．後置の match は必ず `match {` なので，正しいプログラムの読み方は仕様と変わらない
- （補）エフェクトのラベル（issue #255）．`effect AuditLog of Console [default]` は EFFECT_DECL の名前の後ろに EFFECT_LABEL（`of`，PATH，型引数があれば TYPE_ARG_LIST，`default`）を置き，本体の ITEM_LIST を持たない．`of` と `default` は文脈依存の語で，LOWER_NAME のまま読む．ラベルの宣言の後ろに `{ ... }` を書けば，宣言の後ろの改行がないので E0122 になる
- （補）`with` の項目の `AuditLog by HandlerA` は，2つの PATH と `by`（LOWER_NAME）を WITH_BY で包む．右の PATH の後ろには型引数（TYPE_ARG_LIST，`Hits by State[Int]`）を置ける．`by` のない項目は今までどおり PATH だけを並べる．`by` の右に置けるもの（handler，ラベル，エフェクト）は名前解決と型検査が見る
- （補）impl の頭（10.2，17.3）．`impl Map[K: Eq, V: Eq]: Eq` の型と型引数（PATH と TYPE_PARAM_LIST）を IMPL_TYPE で包み，`:` の後ろの Trait は IMPL_DECL の直下の PATH にする．型引数の並びは fn の型引数と同じ TYPE_PARAM_LIST で読むので，`List[Int]` や `Pair[A, A]` も構文としては通る．頭の形の検査（E0328）は型検査に任せる
- （補）handler の頭（8.4）の `:` は HANDLER_DECL の直下に置き，後ろのエフェクトと型引数を HANDLER_EFFECT で包む．`trait Ord: Eq` の `:` と同じ並びなので，fmt は `:` の前に空白を置かない
- （補）前の形（`impl Show for User`，`impl[A: Eq] Box[A]: Eq`，`handler H implements E`）もパーサは診断なしで木にし，validation が E0144 と E0145 を出す．`for` の前の名前を Trait の PATH に，後ろを IMPL_TYPE にし，前置きの型引数の並びは IMPL_DECL の直下の TYPE_PARAM_LIST にする．`implements` は HANDLER_DECL の直下に置いて読み飛ばす．名前解決と型検査が書き換えた後と同じ形で続けられるようにするため
- （補）E0144 の範囲は `impl` から頭の終わり（本体の `{` の前）まで，E0145 の範囲は `implements` の字句．書き換えた頭は `rewrite` モジュールが作り，診断の文面と driver の quickfix の両方が使う．前置きの型引数の制約は，型の後ろの同じ名前の型引数（制約のないもの）に移す（`impl[A: Eq] Box[A]: Eq` は `impl Box[A: Eq]: Eq`）．型に型引数の並びがなければ前置きの並びをそのまま付ける
