# tree-sitter-emela

A [tree-sitter](https://tree-sitter.github.io/) grammar for Emela (`.emel` files), used by
Neovim (`editors/nvim/`) and Zed (`editors/zed/`).

- `grammar.js`: the grammar, following `spec/grammar.md`
- `src/scanner.c`: the external scanner (statement-ending newlines and string bodies)
- `src/parser.c`, `src/grammar.json`, `src/node-types.json`, `src/tree_sitter/`: generated by
  `tree-sitter generate`, committed so that editors can build the parser without the CLI's
  JavaScript runtime
- `queries/`: highlights, locals, folds, indents and text objects, with the capture names of
  nvim-treesitter. Zed's copy of the highlights is derived from them (`editors/zed/sync-queries.sh`)
- `test/corpus/`: tree tests

## Develop

The tree-sitter CLI 0.26.11 (the version that generated `src/`) and a C compiler:

```sh
cd editors/tree-sitter-emela
tree-sitter generate          # after editing grammar.js
tree-sitter test              # test/corpus
tree-sitter parse ../../examples/tour/src/main.emel
scripts/check.sh              # everything CI checks
../nvim/test/run.sh treesitter   # the highlighting in Neovim
```

After changing `queries/highlights.scm`, run `editors/zed/sync-queries.sh`.

## How the grammar reads Emela

The compiler's parser (`crates/emela-syntax`) is the reference. Where the two differ, the grammar
is the more permissive one, since an editor has to highlight code that is still being written.

- A newline is whitespace (an extra) unless the parse state accepts the external token `_newline`
  there and the next line does not continue the current one (`[lex.continuation]`). Inside `(`,
  `[` and `#{` no rule accepts `_newline`, so the innermost-bracket rule (rule 2) follows from the
  parse state; inside a `{` nested in parentheses the block accepts it again.
- To decide whether a line continues, the scanner looks past whitespace, blank lines and comment
  lines at the first meaningful token: a binary operator other than `-`, `.`, `->`, `|`, `else`,
  `escape`, or `match` followed by `{` (rules 1 and 3).
- `fails` and `use` continue a signature (rule 4), and `derive` continues a type, enum or error
  declaration, only where the grammar places the zero-width tokens `_signature_continues` and
  `_derive_continues`. The scanner never produces them; their presence in `valid_symbols` tells it
  that it is at such a position.
- A binary operator at the end of a line reads the next line as its operand (`a = 10 +⏎1`).
  The compiler reports this; the grammar does not.
- The left side of a binding is read as an expression and not checked as a pattern, as the
  compiler's parser does.
- Contextual keywords (`fails`, `derive`, `init`, `release`, `of`, `default`, `by`) are keywords
  only where the grammar expects them (tree-sitter's keyword extraction with `word`). The reserved
  words that have syntax cannot be identifiers anywhere (`reserved`). `as` and the words reserved
  for the future (`[kw.future]`) have no syntax, so they read as ordinary names.
- A string ends at the end of its line when its `"` is missing (E0101), so that the rest of the
  file is not read as a string. A `"""` string ends at a line holding only `"""`; the indentation
  before it is whitespace, not body.
- Any `\` followed by a character is an `escape_sequence`. Invalid escapes (E0107, E0108) are not
  told apart.
